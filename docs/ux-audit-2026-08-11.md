# NE Website Manager — UX and Product Audit

Date: 11 August 2026
Audience: NE clients, administrators, and operators
Scope: authenticated application shell, dashboard, content, collections, navigation, forms, properties, settings, analytics, social, SEO, team, and administration

## Verdict

The application has a reliable technical foundation, but the current product experience behaves more like a database administration interface than a website management workspace. The user's concern is valid: the UI is visually flat, navigation does not adapt enough to the selected website, several visible controls do nothing, and the highest-effort workflows still require manually editing long forms or moving items one step at a time.

The redesign should not become a completely freeform website builder. NE manages custom-coded websites with different capabilities, so the safer direction is a controlled visual CMS: site-specific block registries, sortable structured fields, live previews, templates, bulk operations, and explicit draft/publish states.

No P0 issue was found. The audit identified **8 P1**, **7 P2**, and **2 P3** issues. P1 means the problem significantly impairs a core workflow or creates operational risk.

## Remediation status

The audited P1/P2 usability issues have now been addressed in the implementation: active workspace resolution is shared, visible shell/admin controls work, navigation is capability-driven, editors are responsive, sortable interactions share mouse and keyboard behavior, the dashboard is operational, navigation and forms include live previews, content blocks can be reordered/duplicated/removed, property editing has guided sections and completion feedback, image warnings are resolved, and the Neu Entity white/blue system is applied consistently. The capability migration was applied and verified against the connected Supabase project.

## What is already working

- All 16 representative authenticated routes loaded without a framework error overlay or console error on desktop and mobile.
- The production build succeeds, and the automated suite passes 534 tests across 39 files.
- Once an administrator explicitly selects a client, most data queries are correctly scoped to that client.
- Rich-text editing, preview, autosave/revisions, publication states, confirmation prompts, and toast infrastructure provide a useful foundation.
- Media already supports drag-and-drop upload.
- The responsive navigation drawer works, and most list routes avoid document-level overflow.
- Status chips provide useful explanations for live, draft, archived, and related states.

These strengths mean the product does not need a ground-up technical rewrite. It needs a workflow and interaction redesign built on the existing data model and editor foundations.

## Priority findings

### P1 — Selected website context can disagree across the same screen

**Evidence:** The app layout falls back to the first available client when the selection cookie is absent or invalid (`src/app/(app)/layout.tsx`, around lines 33–38). The dashboard reads the raw cookie without applying the same fallback (`src/app/(app)/dashboard/page.tsx`, around lines 54–65).

**Observed result:** The sidebar displayed “Al-Islah Mosque,” while the dashboard showed the generic “Website Manager” context and recent posts belonging to more than one client. After explicitly changing the client selector, the dashboard became correctly scoped.

**Impact:** An administrator can believe they are operating one website while viewing records from another. Even when the administrator is authorized to see all records, this is a serious multi-client trust and wrong-site-editing risk.

**Recommendation:** Resolve the active workspace in one shared server-side function and pass the same validated client ID to the shell and every route. Never render a selected-site label alongside unscoped data. Add an integration test for missing, invalid, unauthorized, and valid selection cookies.

### P1 — Visible global controls are non-functional

**Evidence:** The top-bar Search element is a non-focusable `div`, while notification and help buttons have no actions (`src/components/Topbar.tsx`, around lines 24–42). Clicking them produced no route, dialog, menu, or state change.

**Impact:** These controls promise capabilities the system does not provide and train operators not to trust the interface.

**Recommendation:** Implement Search as a real command palette that searches content, pages, media, clients, and settings; connect Help to contextual documentation; either implement notifications or remove the bell until it has a meaningful job.

### P1 — Administration row actions do nothing

**Evidence:** Each client row exposes Edit and Users icon buttons without handlers (`src/app/(app)/admin/page.tsx`, around lines 168–175). Browser testing confirmed no navigation, dialog, or state change.

**Impact:** A primary administrative workflow appears available but cannot be completed.

**Recommendation:** Link Edit to a client workspace/settings screen and Users to membership management. Until those destinations exist, replace the controls with a clearly labelled “Not available yet” state or remove them.

### P1 — Core editors are unusable on narrow screens

**Evidence:** Posts, pages, collection entries, and property editors use fixed two-column inline grids such as `1fr 300px` without a responsive breakpoint. On a 390 px viewport, the post editor measured 599 px wide and the property editor 620 px wide, clipping the publishing panel and fields.

**Impact:** Clients cannot reliably edit or publish content from a phone or narrow window.

**Recommendation:** Stack the metadata/publishing panel below the editor at tablet widths, provide a sticky mobile action bar, and move secondary settings into a labelled sheet. Test the entire edit-and-publish path at 390, 768, 1024, and 1440 px.

### P1 — Reordering is implemented as repetitive up/down clicks

**Evidence:** Navigation items, form fields, collection schema fields, and collection entries use small arrow controls. The current code explicitly describes this as simpler than drag-and-drop, and the product plan previously rejected page-builder/drag-and-drop blocks.

**Observed examples:** The Services collection schema contains 13 fields; the Contact/RFQ form contains 8 fields; each item must be moved one step at a time.

**Impact:** Reorganizing real structures is slow, error-prone, and especially painful when moving an item across many positions.

**Recommendation:** Add drag handles and direct reordering with optimistic updates, an Undo toast, and a keyboard-accessible “Move to position…” fallback. Use the same interaction language across navigation, forms, schemas, blocks, media, and repeaters.

### P1 — Navigation management has no information architecture view

**Evidence:** “Add Item” opens a large raw form in otherwise empty space. There is no tree, nesting canvas, visual header preview, or direct manipulation of hierarchy.

**Impact:** Users must translate database fields into a mental model of the final website navigation. This is exactly the kind of CMS task that should be visual.

**Recommendation:** Build a sortable navigation tree with nesting, visibility/status, link validation, per-device preview, and draft/publish controls. Show the corresponding header preview beside the tree.

### P1 — The property workflow is a very long manual form

**Evidence:** The property editor exposes more than 30 inputs plus repeated arrays in one continuous page, with only a small summary/hero area as feedback.

**Impact:** Operators must scan, remember, and validate a large amount of information with little sense of completion or output quality.

**Recommendation:** Organize the workflow into Overview, Details, Location, Media, Features, Availability, and SEO. Make repeaters sortable, support multi-image operations, add completion indicators and validation summaries, and keep a live listing preview visible.

### P1 — The information architecture is not capability-driven

**Evidence:** Most websites receive the same long navigation. “Properties” appears for websites where it is irrelevant, while the Kamal special case claims to be properties-only but still leaves Blog Posts and Pages visible. Zhenghe adds multiple dynamic collection links to an already long sidebar.

**Impact:** Clients see modules that do not belong to their website, and administrators must scan a dense menu before acting.

**Recommendation:** Define enabled capabilities per client and generate the navigation from them. Group site content by real jobs—Manage site, Engage, Measure, Configure—rather than exposing every database entity.

## Important P2 findings

### P2 — The dashboard is a generic status page, not an operating workspace

The welcome gradient, four equal metric cards, recent-content table, and Quick Actions area provide low information density and weak prioritization. On mobile, the cards become a very long single column. There is no “what needs attention” model.

**Recommendation:** Replace vanity-style counters with operational queues: drafts needing review, scheduled publications, stale pages, failed form deliveries, SEO issues, incomplete listings, and recent activity. Let users continue work directly from each item.

### P2 — Editors have ambiguous and duplicated actions

The post editor presents Update at the top, Update Post in the publishing panel, and Save Draft behavior nearby. The distinctions between saving, updating, previewing, and publishing are not consistently expressed.

**Recommendation:** Use one persistent primary action whose label reflects state: Save draft, Submit for review, Schedule, Publish changes. Keep Preview as a clear secondary action and expose saved/autosave status.

### P2 — Form and schema builders are CRUD lists, not builders

Fields appear as repeated cards with arrows and delete actions. Users cannot select a field from a palette, place it visually, preview the result, or configure it in a stable properties panel.

**Recommendation:** Use a three-pane builder: field/block palette, sortable canvas, and contextual property panel. Include live preview and test submission for forms, and sample-entry preview for schemas.

### P2 — Empty states do not teach or accelerate setup

Most empty states simply report that no items exist and ask the user to add the first one.

**Recommendation:** Offer useful starting points: duplicate an existing item, start from a template, import data, or follow a short guided setup. Tailor the next step to the selected website capability.

### P2 — Accessibility basics are inconsistent

The secondary text token `#94A3B8` is approximately 2.56:1 on white and 2.45:1 on `#F8FAFC`, yet it is used for small supporting text and placeholders. Many icon-only controls are unnamed, visual labels are not associated with inputs, custom modal overlays lack dialog semantics, raw inputs suppress outlines, and arrow/delete controls are below comfortable touch size.

The user did not request formal WCAG certification, but these are pragmatic usability problems for every user—not compliance-only concerns.

**Recommendation:** Raise supporting-text contrast, add semantic labels and dialog behavior, establish a visible `:focus-visible` treatment, and use 40–44 px minimum interactive targets. Every drag operation needs a keyboard alternative.

### P2 — Styling is difficult to evolve consistently

Large route components contain extensive inline styles: Settings has roughly 136 inline style blocks, the post editor 87, property editor 82, dashboard 82, and forms 77. Global tokens coexist with hard-coded hex/RGB values; `--border` is declared twice; a dark variant exists without a complete dark palette.

**Recommendation:** Extract layout primitives and product components—workspace header, page header, data list, inspector, publish panel, empty state, builder canvas—and centralize semantic tokens before performing broad visual restyling.

### P2 — Interaction coverage is much weaker than API coverage

The 534 passing tests are valuable, but most cover APIs and libraries. Only one interactive route has a dedicated page test, while key interactions such as client context, dead actions, responsive editors, reordering, and publishing flows are not protected.

**Recommendation:** Add browser-level tests for workspace selection, create/edit/preview/publish, navigation reorder, form building, property editing, and role/capability-specific navigation.

## Minor P3 findings

- Raw `<img>` elements generate optimization warnings and miss the image pipeline's sizing/loading benefits.
- Decorative repeating gradients, the active-sidebar stripe, and numerous low-contrast bordered cards reinforce a generic template aesthetic without improving comprehension.

## Recommended product direction

### Chosen personality

**Capable, calm, and empowering.** The interface should feel like a well-organized operating desk: clear context, confident actions, restrained color, and immediate feedback. It should not look playful, decorative, or like a dense enterprise database.

### Core interaction model

1. **Workspace first:** A prominent website switcher establishes exactly which site is being managed. Site name, environment, last publish, and View site stay visible.
2. **Jobs over tables:** The home screen prioritizes work needing attention rather than equal-weight statistics.
3. **Direct manipulation:** Navigation, form fields, schemas, blocks, repeaters, and ordered entries use the same sortable interaction with Undo and keyboard fallback.
4. **Preview before commit:** Every content/building workflow has a live desktop/mobile preview and an explicit draft-to-publish boundary.
5. **Progressive complexity:** Common settings remain visible; SEO, advanced presentation, and system fields are available without overwhelming the default view.
6. **Capability-driven UI:** Each website exposes only the modules and block types it actually supports.

### Proposed shell

- Top: website/workspace switcher, environment/publish status, global command search, contextual help, profile.
- Left: Home, Content, Structure, Media, Forms, Measure, Settings; sections expand only when supported by the selected site.
- Main header: breadcrumb, page title, contextual status, View site/Preview, and one state-aware primary action.
- Optional right inspector: publishing, field/block settings, or item metadata depending on the task.

## Drag-and-drop redesign

### Navigation builder

- Sortable nested tree with drag handles and explicit drop zones.
- Live desktop/mobile header preview.
- Internal-page picker, external-link validation, visibility rules, and role-safe destructive actions.
- Draft changes, publish, revision history, and Undo.

### Form and collection-schema builder

- Left palette of supported field types and reusable groups.
- Center canvas with direct reorder, grouping, conditional logic, and empty drop zones.
- Right properties panel for label, key, required state, validation, help text, and presentation.
- Preview/test mode using realistic sample data.

### Content/page builder

Use a **controlled block registry**, not unrestricted HTML or arbitrary layout placement. Each site registers approved components—Hero, Rich text, Gallery, CTA, FAQ, Services, Testimonials—with validated fields and design constraints. Editors can add, reorder, duplicate, hide, and configure blocks while the website remains on-brand and technically safe.

### Collection entries and properties

- Drag-sort ordered entries and repeated values.
- Multi-select and bulk publish/archive/delete.
- Duplicate from an existing entry or template.
- Import/export where volume makes manual entry inefficient.
- Visual media organization and meaningful previews.

## Implementation roadmap

### Phase 0 — Restore trust and basic usability

1. Centralize active-client resolution and eliminate mixed-client dashboard states.
2. Implement or remove dead Search, Help, Notifications, Edit, and Users controls.
3. Fix responsive editor layouts and add semantic labels, focus states, dialog behavior, and adequate targets.
4. Add browser tests for these trust-critical paths.

### Phase 1 — Rebuild the shell and information architecture

1. Introduce the explicit website workspace header.
2. Generate navigation from per-site capabilities.
3. Replace dashboard vanity cards with work queues, activity, and contextual shortcuts.
4. Add a real command palette and recently edited items.

### Phase 2 — Introduce a shared builder system

1. Establish shared drag-and-drop primitives, keyboard movement, optimistic persistence, revision handling, and Undo.
2. Migrate Navigation first because hierarchy and ordering provide the clearest value.
3. Migrate Forms and Collection Schemas to the three-pane builder.
4. Add sortable collection entries, repeaters, and bulk operations.

### Phase 3 — Visual content management

1. Define approved block schemas per website/template.
2. Build the block canvas, contextual inspector, and live responsive preview.
3. Refactor Properties into grouped steps with preview and media workflows.
4. Unify draft, autosave, review, schedule, and publish behavior across modules.

### Phase 4 — Automation and scale

1. Add templates, duplication, imports, bulk changes, and scheduled publishing.
2. Surface delivery failures, stale content, SEO issues, and incomplete records as tasks.
3. Add optional assisted metadata/content suggestions only where users can review the output before publishing.

## Dribbble reference takeaways

The reviewed [CMS search gallery](https://dribbble.com/search/CMS), [CMS Builder](https://dribbble.com/shots/26071905--CMS-Builder), [Blog CMS Article Page Builder](https://dribbble.com/shots/26453356-Blog-CMS-Article-Page-Builder-UI), and [No-code CMS Collection Builder](https://dribbble.com/shots/27524763-CMS-Collection-No-Code-Website-Builder) consistently show useful patterns: strong workspace context, split editor/publishing layouts, form/block-based creation, visual canvases, and direct manipulation.

The references should be treated as interaction inspiration, not usability evidence. The NE redesign should borrow their clarity and visual preview patterns while avoiding decorative dashboards and unconstrained no-code behavior that could break custom websites.

## Definition of success

The redesign is successful when a client can select their website, understand what needs attention, find any item, visually restructure navigation/forms/content, preview the result, and publish confidently without understanding the underlying database model. An operator should be able to perform the same work across multiple client sites without losing context or repeating avoidable manual entry.
